# 技术架构与决策

状态：总体架构已确认，原生宿主与受限 XPC 运行时已落地；完整边界仍需分阶段验证。文中性能数值为验收目标，不是实测结果。实际证据见 [验证记录](../developer/VALIDATION.md)。

已确认约束：底座不内置具体业务功能；应用搜索、计算、翻译等均通过可启停插件提供。底座只负责通用 UI、生命周期、运行时和受权限控制的系统能力。详见 [插件底座边界](../architecture/PLUGIN-FOUNDATION.md)。

## 1. 推荐技术路线

| 层 | 推荐 | 原因与代价 |
| --- | --- | --- |
| 桌面宿主 | Swift + AppKit；设置和辅助页面可用 SwiftUI | 控制搜索框、输入法、焦点和原生窗口；需要维护原生渲染器 |
| 搜索与动作 | Swift 服务；版本化 JSON 协议 | 扩展不能堵塞 UI 主线程；核心行为由宿主统一管理 |
| 标准扩展执行 | 受 App Sandbox 限制的 XPC 执行服务 + JavaScriptCore | 默认不暴露文件、网络、进程能力；通过宿主代理访问 |
| SDK | TypeScript；查询 API 先行，React 组件桥接随后提供 | 查询扩展开发成本低；复杂 UI 的桥接需专门验证 |
| 构建与 CLI | Node.js 工具链、TypeScript、esbuild | Node 用于开发构建，不代表标准扩展运行时支持 Node 内置模块 |
| 存储 | SQLite；凭据使用 macOS Keychain | 本地优先；普通数据与密钥分离 |
| 索引 | 首选系统能力并测量；必要时补充自有索引 | 文件搜索范围、中文排序、数据更新要实测 |
| 商店 API | TypeScript 服务 + PostgreSQL + 对象存储 | 版本元数据与不可变包分离；托管厂商后定 |
| 文档站 | Markdown/MDX，API 参考由类型与 schema 生成 | 文档与 SDK 同仓库、同版本验收 |

若未来跨平台成为优先目标，可评估 Tauri 或 Electron 宿主。当前不优先它们，是为了先验证 macOS 输入与焦点体验，而非声称网页技术无法实现。

### 为什么不直接把 Node worker 当公共扩展沙箱

Node 的权限模型并不保证限制恶意代码；`node:vm` 也不是不可信代码的安全隔离方案。多进程/worker 主要用于故障和性能隔离，不能独立支撑商店的权限承诺。[Node 权限文档](https://nodejs.org/api/permissions.html)、[Node VM 文档](https://nodejs.org/api/vm.html)

本方案将公共扩展限制在标准 SDK 中。需要 shell、Node 原生模块、任意磁盘访问的代码进入明确标记的「本地可信脚本」模式；该模式不纳入初期公开商店。

## 2. 模块边界

```text
apps/macos/                 原生客户端、窗口、输入、渲染与系统能力
services/extension-host/    受限执行服务、JSContext、IPC、资源看门狗
packages/protocol/         版本化消息与 JSON Schema
packages/sdk/              查询、动作、状态与能力接口
packages/ui/               React 组件与声明式 UI 树
packages/cli/              创建、开发、检查、测试、打包与提交
packages/testkit/          假宿主、模拟服务、回放与断言
extensions/youdao/         首个真实扩展
extensions/calculator/     无网络示例
services/registry/         商店、版本、发布、审核 API
apps/store/                商店网页与作者后台
docs/                     用户与开发者文档
```

这是完整规划的目录，其中宿主、执行服务、SDK/CLI、计算器/应用搜索/文本工具/有道插件已实现；其他目录按阶段建设。实际状态以开发验证文档为准。

## 3. 查询管线

`输入事件 → 输入法状态判断 → 前缀解析 → Provider 路由 → 缓存/防抖 → 查询 → 校验 → 合并排序 → 原生渲染`

- 查询带 `sessionId / queryId / commandId / generation`。只有当前 generation 的结果可以进入 UI。
- 输入更改、语言切换、关闭窗口、扩展重载都会取消旧查询；宿主在结果入口再次检查 generation，不能只依赖扩展自行尊重 AbortSignal。
- 本地查询可以即时运行；联网查询默认防抖 350ms，可声明更长间隔和最小输入长度。限流计数由宿主按服务和扩展维度管理。
- 扩展可一次返回，也可逐批返回；每批必须包含稳定 item ID。选中项依 ID 保持，不依数组下标。
- 扩展内部 rank 只影响本扩展排序。宿主决定组顺序，扩展不能靠无限高分劫持全局首位。
- 主框每个 Provider 初始最多接收 50 条，总渲染结果有上限；超过部分通过分页或继续加载获取。
- 默认关键词扩展未命中前缀时不会收到输入；已声明并获准 `inputMode: query` 的扩展可接收未被关键词接管的非空输入。清空查询后终止相关请求，不保留旧可执行结果。

## 4. 查询与执行分离

查询阶段仅允许声明过的查询能力：网络检索、读取扩展自身数据、受范围限制的文件检索。剪贴板写入、打开应用、运行脚本等只能由用户动作或已授权自动化执行。

动作需要宿主生成的一次性调用上下文，绑定扩展身份、包版本、命令、结果和当前状态。扩展不能自行构造身份或重用另一扩展的调用凭据。动作执行时重新检查权限和目标，不仅在安装时检查一次。

部分「只读网络查询」也会上传用户输入或产生服务费用。安装页和设置须说明请求域名和触发方式；是否自动查询由用户的扩展设置决定。

## 5. 执行隔离与能力代理

标准运行时不提供 Node `fs`、`child_process`、原生 addon、任意模块动态下载或直接 Objective-C 桥接。npm 中可打包为纯 JavaScript、仅依赖已声明 Web/SDK API 的库可以使用；CLI 对不支持的导入直接报错。

网络、存储、Keychain、剪贴板、应用启动、文件选取等通过宿主代理。XPC 对端身份、可用能力和扩展会话在建立连接时绑定；收到消息后做 schema 校验、大小限制、资源范围校验和超时处理。

**沙箱能否实现所需限制是 A 阶段的阻塞验证项，不是已经解决的事实。** 需要验证签名后的执行服务在宿主拥有辅助功能或目录授权时，仍不能绕过代理读取用户文件、访问网络、调用其他扩展秘密。不得把 JSContext 隔离本身当 OS 沙箱。

XPC 服务实例与扩展之间的进程映射先做实测；不假设建立多个连接就自动得到多个进程。若服务共享进程，必须清楚定义崩溃影响范围。首版可以采用串行前台扩展会话，超时终止执行服务并恢复宿主；并发后台扩展在确认隔离与调度设计后开放。

JSContext 的同步死循环不能依靠普通 JS 定时器取消。看门狗运行在宿主，必要时重启执行服务。崩溃扩展被暂时禁用，其余原生查询继续运行。

### 初始能力列表

| 能力 | 范围 |
| --- | --- |
| `network` | 声明域名；重定向逐跳验证；默认不允许本地网络目标 |
| `clipboard.write` / `clipboard.read` | 分开授权；读取不能伴随每次输入自动发生 |
| `selection.read` | 用户指定的选区动作 |
| `storage` | 扩展命名空间；有限容量；普通数据 |
| `secrets` | 扩展命名空间的 Keychain 字段 |
| `files.read` / `files.write` | 用户授予的目录或文件句柄，不接受任意字符串路径扩大范围 |
| `applications.open` | 经用户执行动作后打开明确目标 |
| `windows.manage` | 需要系统辅助功能授权 |
| `notifications` | 状态提示；不承担隐式后台运行权 |
| `background` | 后续支持的任务类型、频率及预算 |

升级新增域名或权限时先展示差异，未确认前继续使用旧版本。平台权限与 macOS TCC 权限分别呈现，不声称勾选扩展权限就能绕过系统授权。

## 6. 存储与恢复

SQLite 至少包含：扩展安装记录、版本状态、别名/快捷键、权限授予、偏好、收藏、使用排名、迁移版本、任务记录。扩展数据独立 namespace，密钥不在普通数据库中明文存储。

包内容不可变；可写数据单独存放。升级先备份或事务化迁移数据，再切换版本。回滚代码若不兼容新数据，必须恢复对应快照或拒绝无损回滚，并解释原因。

翻译查询默认不持久化。开发日志不记录密钥、剪贴板正文或选区内容；需要重放时由开发者明确选择测试输入。诊断默认本地查看。

云同步后置设计：按类别启用，定义冲突策略、删除墓碑、离线队列、设备撤销；密钥、文件索引和剪贴板历史不因启用设置同步而自动上传。

## 7. 性能预算与验证方法

| 指标 | 初始目标 | 测法 |
| --- | --- | --- |
| 常驻后唤起到可输入 | p95 ≤ 150ms | 指定测试机、100 次冷热状态分开记录 |
| 本地输入到首批结果 | p95 ≤ 100ms | 约定规模的应用/文件数据集 |
| 宿主收到扩展结果到渲染 | p95 ≤ 50ms | 使用本地 fixture 排除外网延迟 |
| 旧结果串入新查询 | 0 次 | 随机延迟、取消、乱序响应测试 |
| 单次 IPC 大小 | 初始上限 2MiB | 超限拒绝且宿主继续工作 |
| 主框失去响应 | 不因扩展死循环发生 | 无限循环、内存增长、畸形输出测试 |

外网翻译耗时由服务决定，只对本地调度与反馈设置预算。内存和电量在 A/B 阶段形成基线后设硬指标；不预先宣称低于某个未测数值。

## 8. 必须先验证的技术问题

1. AppKit 搜索输入与中文输入法、焦点归还、多屏/Spaces 是否达到目标。
2. JavaScriptCore 的 Promise、模块打包、取消信号、定时器和 SDK 桥接能否形成一致运行环境。
3. 签名 XPC helper 的沙箱限制与宿主能力代理是否可验证；服务崩溃与失控后的恢复策略是否可用。
4. 开发模式能否通过 Web Inspector 断点定位到 TypeScript 源码。WebKit 提供 JSContext 可检查机制，但还需验证本项目的进程与 source map 链路。[WebKit 调试说明](https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/)
5. React 声明式 UI 到原生列表的桥接是否满足状态更新和选择稳定性；不通过时首版 SDK 先提供结构化 UI，暂缓 React 包。

以上问题在 A 阶段产生实测记录和 ADR。若验证失败，更新技术方案并列明开发体验与兼容性的变化，不能静默用不受限 Node 运行时替代既定权限承诺。
